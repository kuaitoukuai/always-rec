# AlwaysRec 功能与代码检查报告

> 检查日期：2026-11-06  
> 检查范围：README、`docs/`、Android 客户端、Python 后端及构建配置。  
> 检查基线：当前工作区；其中 `app/build.gradle.kts` 已显示版本 `0.2.0`，并包含尚未提交的多设备支持改动，而多数文档仍描述 `0.1.0`。  
> 说明：本次只检查和新增本文档，没有修改业务代码。静态确认表示可以从控制流直接确定，不代表已完成真机或云服务验证。

## 一、结论

项目已经具备完整的原型主链路：前台录音、能量 VAD、8 秒预缓冲、AAC/ADTS 分片、本地转写、Wi-Fi 上传、心跳、后端缓存、小时/日概要和网页看板均有实际代码，当前 Android Debug 包可以编译成功。

但它仍不宜按“全天候可靠记录”或“可直接分发”的标准使用。最重要的结论是：

1. **手机上传的转写文本完全没有被后端消费**，文档中的“复用文本、不重复计费”目前不成立。
2. **网盘下载不是原子的**，中断留下的半截文件会被后续同步当成完整文件，可能进一步形成错误的永久转写缓存。
3. **录音进程异常退出会留下孤儿音频**，重启后没有恢复机制，这些音频不会进入上传队列。
4. **上传、转写和概要存在并发/状态边界问题**，可能漏处理、重复调用 ASR，或把概要保存到错误日期。
5. **安全边界没有根本改善**：凭据改为 `BuildConfig` 注入只能避免直接写进源码，不能避免从 APK 中提取；网页仍无鉴权，音频和文本仍以明文经过第三方网盘。

建议优先修复数据完整性和重复计费问题，再补自动化测试与长时间真机验证。

## 三、高优先级问题

### P1-1：后端忽略手机上传的 txt，必然重复转写

**证据**

- `app/src/main/java/com/daluo/alwaysrec/Upload.kt:294-311` 会上传 `${meta.id}.txt`。
- `backend/pipeline.py:171-187` 只处理文件名以 `.aac` 结尾的项目，直接跳过 `.txt`。
- `backend/pipeline.py:237-247` 在没有本地 JSON 缓存时总是调用 `transcriber.transcribe()`。

**实际复现**

使用假网盘和临时目录，让远端同时存在一个 `.aac` 和同名 `.txt`。结果只下载 `.aac`，下载列表中没有 `.txt`。

**影响**

- 手机端已经付费/耗时生成的文本不能降低后端 ASR 调用量。
- README、架构文档和 Changelog 中“后端优先复用”“不重复计费”的描述与实际不符。
- 空文本片段也不会上传“已处理”标记，后端会再次处理这些片段。

**建议**

同步同名 txt，并按 `(device, clip_id)` 转成现有 JSON 缓存；空文本也应写成空数组。只有缓存不存在时才调用 ASR。增加“已有 txt 时 transcriber 零调用”的测试。

### P1-2：伴随文本上传失败被忽略，音频完成后文本永不自动补传

**证据**

`app/src/main/java/com/daluo/alwaysrec/Upload.kt:306-313`：

- `uploadCompanion()` 的布尔返回值没有参与 `ok` 的计算。
- 无论 txt 是否上传成功，只要音频成功，就执行 `spool.markAttempt(meta, ok)`。
- 成功后音频和 meta 移到 `done`，后续 `spool.pending()` 不再返回该片段。
- `HttpPutSink` 默认不支持伴随文本，但同样会被标记为音频上传完成。

**影响**

弱网下容易形成“网盘有音频、没有文本”的永久状态；即使 P1-1 修复，后端仍会重复 ASR。

**建议**

将音频和转写分别维护投递状态，或把必需伴随文件的成功纳入整体成功条件。不要把不支持 companion 的 sink 静默当成完整成功。

### P1-3：下载中断会留下残缺文件，后续同步不再重下

**证据**

- `backend/baidu_pan.py:237-249` 直接向最终目标文件写入，没有 `.part` 临时文件和原子重命名。
- `backend/pipeline.py:175-183` 只判断 `local_file.exists()`；存在即跳过下载，没有校验远端大小、MD5 或音频完整性。
- 一旦残缺文件转写成功，`backend/pipeline.py:247` 还会把结果保存成正常缓存。

**实际复现**

模拟第一次下载写入 `partial` 后抛异常，第二次恢复网络：

- 第一次得到 0 个片段；
- 第二次没有再次调用下载；
- 第二次却把残缺文件作为 1 个有效片段返回，内容仍为 `partial`。

**影响**

音频永久不完整、时长错误、缺话，甚至错误文本被缓存；后续网络恢复也无法自愈。

**建议**

下载到同目录临时文件，正常结束后原子替换；异常时删除临时文件。记录远端 `size`/MD5 并校验，至少不能用“路径存在”代表下载完成。

### P1-4：进程被杀或崩溃后，正在写入的音频成为不可上传的孤儿文件

**证据**

- `Capture.kt:279-307` 在片段开始时就创建 `.aac`。
- `.meta` 只有正常封口时才由 `Capture.kt:325-326`、`Spool.kt:46-57` 写入。
- `Spool.kt:59-63` 的 `pending()` 只枚举 `.meta`，不会恢复只有 `.aac` 的文件。

**影响**

ROM 杀进程、崩溃或设备断电时，当前片段虽然可能保留了可解码的 ADTS 数据，但重启后既不上传，也没有明确失败提示。这与“先落盘、绝不丢数据”的强表述不一致。

**建议**

服务启动和 Worker 执行前扫描无 meta 的音频，修复/封口可解码部分并补建 meta；正常封口采用临时文件加原子重命名。需要模拟进程死亡验证，而不只是调用正常停止按钮。

### P1-5：后台自动同步只处理“今天”，跨天补传的数据不会出现

**证据**

`backend/server.py:329-334` 每轮固定执行 `sync_once(today)`。`collect_pan()` 虽支持全日期和指定日期，但看板后台没有扫描历史日期或补同步窗口。

**影响**

- 前一天录制、第二天才上传成功的音频不会被看板自动拉取。
- 后端停机跨天后，缺失日期只能人工运行 CLI 补处理。
- 预缓冲时间戳偏差还可能在午夜附近放大日期归属问题。

**建议**

每次至少滚动同步最近若干天，并维护远端清单游标/文件状态；启动时执行一次全量对账，之后增量处理。

### P1-6：转写与上传 Worker 存在漏调度和重复调用窗口

**证据**

- `Transcribe.kt:48-62` 开工时只取一次 `todo` 快照。
- 新片段封口使用 `ExistingWorkPolicy.KEEP`（`Transcribe.kt:28-39`）；若旧任务正在运行，新任务不会排队，旧任务也不会再次扫描新片段。
- `Upload.kt:238-280` 的周期任务、Wi-Fi 任务使用不同唯一名，手动 `runNow()` 又不唯一，它们可以并行。
- `Upload.kt:294-303` 也会补做 ASR，与 `TranscribeWorker` 之间没有锁或原子“认领”状态。

**影响**

- 新片段可能要等下一次事件才转写，违背“封口即转写”。
- 两个 Worker 可同时判断“尚无文本”，造成重复 ASR 请求和费用。
- 并发上传会增加重复请求、meta 竞争和 rename 失败概率。

**建议**

统一串行调度，使用互斥和原子处理状态；任务结束前再次扫描，或使用可靠的追加/重排策略。为“运行中又来新片段”和“两个 Worker 同时处理同一片段”补测试。

### P1-7：`llm` 配置没有生效，默认 `enabled=false` 也不能阻止概要调用

**证据**

- `backend/config.example.json:19-23` 提供 `llm.enabled/base_url/api_key_env/model`，默认 `enabled=false`。
- `backend/llm.py:15-23` 实际只读环境变量或 `asr.api_key`。
- `backend/llm.py:26-46` 使用固定 URL 和默认模型，没有读取 `CFG["llm"]`。
- `backend/server.py` 的 `ensure_hourly()`、`ensure_daily()` 直接调用 `llm.chat()`，没有检查开关。

**影响**

用户以为关闭 LLM 时，只要 ASR key 可用，打开页面仍会发送文本并产生调用；自定义 LLM 端点和模型也不会生效。

**建议**

显式注入 LLM 配置，首先检查 `enabled`，再使用配置的 base URL、key 环境和模型；无配置时页面应显示明确状态，而不是静默无概要。

### P1-8：代码声称超过 4 分钟会切片，实际手机和后端都整段发送

**证据**

- `backend/asr.py:177-181` 注释明确说“超过 4 分钟的片段会先切片再识别”。
- `backend/asr.py:196-235` 实际读取整个文件并发送一次请求，没有切片。
- `Capture.kt:31` 允许片段达到 300 秒；`AliyunAsr.kt:42-87` 同样整段 Base64 编码后发送。

**影响**

最长片段可能撞上云端时长限制，恰好丢失信息量较高的长对话；失败后主要依靠重试，无法解决确定性超限。

**建议**

实现真实切分并映射回时间戳，或把采集上限降到已验证的安全范围；增加 240 秒、300 秒两个边界的集成测试。

## 四、中优先级问题

### P2-1：片段时间戳没有扣除预缓冲，最多偏移约 8 秒

`Capture.kt:297` 在 VAD 触发后才设置 `startedAt`，而 `Capture.kt:302-305` 随后把最多 8 秒 ring buffer 写入片段。文件名和 `startedAt` 因此表示触发时间，不是音频实际开始时间；`durationMs` 却包含预缓冲。

影响是 App、后端时间线和远程日期目录均可能偏移，午夜附近还可能归错日期。建议根据实际写出的预缓冲帧数回推 `startedAt`。

### P2-2：切换日期期间生成概要，结果可能保存到另一天

`SummaryActivity.kt:219-251` 启动协程时没有固定请求日期，网络返回后在 `SummaryActivity.kt:248` 使用可变的成员 `day` 保存。用户在等待期间切换日期，就可能把旧日期的概要写进新日期。

建议在点击时保存 `requestedDay`，返回后仍写回该日期；若当前页面已切换，不要直接用旧结果覆盖当前视图。

### P2-3：网盘列目录只取前 1000 项，没有分页

`backend/baidu_pan.py:68-79` 固定 `start=0, limit=1000`，所有同步和心跳列举都复用该函数。单日或设备目录超过 1000 项后，其余文件不会进入处理。

建议按 `start` 翻页直到返回为空，并测试恰好 1000、1001 项的边界。

### P2-4：默认依赖清单不能保证看板显示录音时长

`backend/server.py` 的统计依赖 `probe_duration_ms()`，后者需要 PyAV；但 `backend/requirements.txt` 将 `av` 注为可选。默认云端 ASR 虽不需要本地解码，看板时长统计却仍需要它。全新环境只安装 requirements 时，异常被吞掉并返回 0。

本机已安装 PyAV 19.0.2，样例 `test_rec.aac` 测得 14747 ms，说明当前环境可用；问题在于全新部署依赖声明不完整。建议把看板所需依赖列为核心依赖，或提供无 PyAV 的 ADTS 时长计算。

### P2-5：失败不可见且大量异常被吞掉，难以定位线上问题

上传、转写、心跳、编码器和同步多处使用 `runCatching`/`except` 后返回 false、null 或 0。现有文档已承认这一点，本次检查确认仍普遍存在。特别是心跳上传结果、伴随文本上传结果和权限申请结果都没有向用户展示。

建议至少保留分类日志和最近错误状态，区分网络、凭据、配额、编码、权限和云端限制；永久失败不能只靠 20 次后静默跳过。

## 五、文档与实现不一致

1. **版本不一致**：当前 Gradle 为 `0.2.0`，README、VERSION 和 Changelog 仍以 `0.1.0` 为主。
2. **凭据配置方式已变化**：README 和 `docs/SETUP.md` 仍要求编辑 `LocalConfig.kt`；当前代码已从 `local.properties` 注入 `BuildConfig`。
3. **远程目录结构已变化**：当前 App 使用 `/录音记录/<设备>/<日期>/`，心跳为 `_状态/<设备>.json`；架构文档仍只写旧的单设备布局。
4. **文本复用描述不真实**：README、ARCHITECTURE 和 Changelog 的“后端复用 txt”与 P1-1 冲突。
5. **后端 README 缓存描述过时**：`backend/README.md:42` 仍写 `data/state.json`，实际使用 `data/transcripts/*.json`。
6. **同步周期注释不统一**：`server.py` 文件头和页面写 5 分钟，实际入口以 60 秒启动同步线程。
7. **首次构建说明不完整**：仓库没有 `gradlew`/`gradlew.bat` 和 wrapper 文件，文档要求先执行 `gradle wrapper`，但环境要求没有明确“需预装系统 Gradle”。干净环境不能直接照 `./gradlew assembleDebug` 执行。
8. **“手机只负责采集”已不符合混合架构**：README 开头和 backend README 仍有此表述，实际手机负责 ASR 和本地概要。DESIGN 已说明该妥协，其他入口文档应同步。

## 六、安全风险复核

以下是原 `docs/EVALUATION.md` 已列出、本次确认仍成立的风险：

- **APK 凭据可提取**：`BuildConfig` 注入改善的是源码泄漏风险，不是 APK 反编译风险。BDUSS 和 API Key 最终仍进入客户端常量。分发前仍需运行时安全存储、受限凭据或后端中转。
- **看板无鉴权**：默认绑定 `127.0.0.1` 是正确默认值；一旦绑定 `0.0.0.0`，必须有可信反向代理认证，不能把 Flask 页面直接暴露到公网。
- **音频和文本明文上云**：全天对话属于高敏感数据，当前没有端到端加密。
- **多设备身份不是安全边界**：设备别名和 Android ID 哈希用于隔离文件，不应被当成认证机制。
