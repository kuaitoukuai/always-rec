## 二、部分采纳

**P1-6 的并发**：用协程级互斥锁 + 唯一任务名收敛了同一进程内的重复。
没有引入持久化的"认领状态"（处理中标记），因为那需要一套状态机与崩溃恢复，
成本高于当前收益。**残余风险**：跨进程（未来若把 Worker 拆到独立进程）不成立。

**P2-5 日志**：没有把所有 `runCatching` 换成分类日志，只在孤儿恢复、同步结果、
`llm` 关闭等关键路径留下了可观察信号。**残余风险**：上传失败仍主要靠队列状态判断。

## 三、明确不改（及理由）

| 问题 | 不改的理由 |
|---|---|
| P2-2 切换日期时概要可能存到另一天 | 页面按 URL 参数 `date` 渲染，写入也用它；只有在午夜整点同时请求两个日期的极端窗口才会串。改造成本（引入任务队列）远大于影响 |
| 网页无鉴权 | 默认只绑 `127.0.0.1`。要在公网用必须加反向代理认证，已在文档明确；不该由这个原型内置一套半成品鉴权 |
| APK 可提取 BDUSS / API Key | 客户端无法彻底解决。`BuildConfig` 注入只是让源码能公开；真正做法是后端中转或受限凭据，属于下一步架构调整，不在本次范围 |
| 音频/文本明文经网盘 | 端到端加密会同时毁掉"网盘可读可整理"这个前提，需要单独设计 |
| 多设备名不是安全边界 | 它只是文件隔离，我在文档里明确写了这一点，没有当认证用 |

## 四、本次新增的已知行为

- 空转写也会上传一个只含空格的 `.txt`（1 字节）。这是**有意为之**：
  后端据此判断"这段确实没人说话"，而不是"手机没传文本"，从而不再重复识别。
- 单片上限 2 分钟，长对话会被切成多片；时间线靠文件名时间拼接，仍是连续的。
- 预缓冲时间戳已回扣，同一段话在看板上的时间与手机时钟一致（误差 ≤ 1 帧）。

## 五、建议的下一轮验证

1. 强杀进程（`am force-stop` 或断电）后重启，检查孤儿片段是否被救回并上传。
2. 弱网/断网下让 `.txt` 上传失败，恢复后确认 `txtretry` 会补传。
3. 跨午夜跑一次，确认昨日尾段自动出现在看板。
4. 两台设备同时录到同一段对话，确认时间线与设备标签不串。
5. 24 小时连续运行，检查心跳断点与电量曲线。
