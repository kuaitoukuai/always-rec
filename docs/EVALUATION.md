# 自评与已知问题

> **这份文档是专门为对抗性审查准备的。**
> 它主动列出本项目的弱点、未经验证的假设、以及可以攻击的设计点。
> 如果你要评估这个项目，请从这里开始，而不是从 README。

---

## 一、一句话定性

**一个已经跑通的个人原型，不是生产级产品。**

它在真机上完成了从录音到日报的完整闭环，但所有验证都基于
**单设备、单用户、1 小时以内的数据量**。把它当成「可以自己用的工具」是合理的，
当成「可以给别人用的软件」则远远不够。

## 四、缺陷清单

### P0 —— 阻断性问题（给别人用之前必须解决）

**P0-1：BDUSS 编译进 APK**
`LocalConfig.kt` 里的网盘 cookie 会被打进 APK。任何人反编译
（`apktool d` 即可）就能拿到完整的网盘登录态，可以读写用户**整个网盘**。
正确的做法是运行时输入 + Keystore 加密存储，或改用后端中转。

**P0-2：Web 页面无鉴权**
`server.py` 没有任何认证。用 `--host 0.0.0.0` 暴露到局域网/公网时，
任何人可以看全部录音文字和概要。文档里提了要加 Basic Auth，但代码没实现。

**P0-3：无说话人分离**
多人对话时所有内容混成一段。一场三人会议的时间线无法阅读——
不知道谁承诺了什么。这是「能不能用于会议记录」的分水岭。

### P1 —— 严重问题

**P1-1：依赖百度网盘非官方接口**
网页版接口（`app_id=250528`）没有 SLA，百度随时可能改。
一旦失效，整个上传链路瘫痪，而且没有 fallback。

**P1-2：单点依赖阿里云**
转写只用 `qwen3-asr-flash`。虽然代码里有 `local` 和 `groq` 两个后端，
但本地模型质量不可用（见下），Groq 未实测。阿里云涨价/停服即不可用。

**P1-3：心跳也依赖网盘**
设备存活的判断依赖网盘写入。如果网盘接口挂了，
监控会显示「设备离线」，但实际设备在正常录音——**误报**。
监控系统本身成了单点。

**P1-4：零单元测试**
全部靠真机手工验证。任何重构都可能引入回归且无法快速发现。

**P1-5：大量吞异常**
`runCatching { ... }.getOrDefault(false)` 在代码里出现约 20 次。
失败原因被完全丢弃，线上问题无法定位。例如上传失败时，
无法区分「网络问题」「凭据过期」「配额超限」。

**P1-6：本地 whisper 方案名存实亡**
`asr.py` 里保留了 `LocalWhisper`，但实测 small 模型在远场对话上
错字连篇且吐繁体（「宇宙你好」「鐵盒」）。保留它会给用户错误预期。

### P2 —— 体验与维护性问题

| 编号 | 问题 |
|---|---|
| P2-1 | `SummaryActivity` 全程序化 UI，改动成本高，无 XML 布局 |
| P2-2 | `server.py` 单文件约 500 行，同步/摘要/页面混杂 |
| P2-3 | VAD 误触发率高，实测 63 段里约一半是噪声或空 |
| P2-4 | 无跨天检索能力（问不了「上周三那个想法」） |
| P2-5 | 后端用 `glob` 扫目录，1 年后 3.6 万文件可能变慢 |
| P2-6 | 中文硬编码，无国际化 |
| P2-7 | 失败状态不可见——上传永久失败的文件只能等 20 次重试后静默跳过 |

## 五、设计争议点（可以攻击的地方）

### 争议 1：为什么转写放在手机端？

原本的架构是「手机只录，后端全包」，更符合关注点分离。
改成手机端做转写，是因为用户要「立刻看到文字」，而网盘同步有 1–2 分钟延迟。

**反对意见**：这是为了体验牺牲架构纯洁性。代价是 API Key 必须存在手机上
（P0-1 的根源）。更干净的方案是手机直连自建后端，但那要求后端有公网地址。

### 争议 2：用网盘当消息队列

**支持**：零成本、零运维、跨设备、天然归档。

**反对**：把一个消费级同步盘当基础设施，是典型的「用玩具做生产」。
没有投递语义、没有重试策略、没有顺序保证、没有并发控制。
真正的消息队列（哪怕是 Redis）都更合适。

### 争议 3：能量 VAD 而不是 DNN

**反对意见**：2026 年了还在用能量阈值做 VAD，误报率必然高。
Silero VAD 只有 1.5MB，手机上跑得动。

**辩护**：24 小时 × 每秒 50 次 = 432 万次推理/天。CPU 唤醒的耗电
会盖过它省下的存储收益。实测证明误触发的主要成本是「多录几段空音频」，
而空音频的转写会被过滤掉，实际损失有限。

**折中方案（未实施）**：能量法做粗筛，命中后才跑 DNN 确认。这样 DNN 调用次数
降到百分之一，兼顾精度和功耗。

### 争议 4：不做端到端加密

音频和文本以明文存在百度网盘上。百度可以看到全部内容。

**辩护**：这是「用网盘」这个选择的必然代价，如果要加密，
就必须自建存储，整个成本模型崩塌。

**但必须承认**：对于一个「记录全天对话」的产品，把明文放在第三方云盘上，
在隐私上是站不住的。

## 六、给审查者的攻击面建议

如果你想找出这个项目的问题，按以下顺序进攻，收益最高：

1. **让它跑 24 小时**，看心跳断在哪里、内存涨多少、电量掉多少
2. **断网 30 分钟后恢复**，看队列是否完整、有无重复上传、有无文件损坏
3. **同时跑两台设备**，看网盘目录冲突、后端同步是否错乱
4. **连续录 8 小时不停说话**，看单片 5 分钟切分是否稳定、有没有内存泄漏
5. **检查 ADTS 文件用 ffmpeg 解码**是否报警告（我只验证了帧结构对齐，
   没验证音频内容是否正确）
6. **审 `SegmentEngine` 的边界条件**：open/close 竞态、ring 溢出、编码器异常
7. **审 `BaiduCookieSink` 的 URL 编码**：路径含中文/空格/特殊字符时是否正常
8. **审 `server.py` 的时间分组**：跨午夜、时区、夏令时
9. **尝试让 LLM 概要产生幻觉**：喂它全是噪声的时间线，看会不会编造内容
10. **检查 `.gitignore` 是否真的挡住了凭据**（我扫过一遍，但可能有遗漏）

## 七、如果重做，会怎么改

1. **凭据不进 APK**：改为首次启动时扫码/输入，存 EncryptedSharedPreferences
2. **存储换成 S3 兼容**：MinIO 自建或腾讯云 COS，用预签名 URL
3. **加说话人分离**：阿里云有 diarization 能力，或本地 pyannote
4. **补单元测试**：至少覆盖 `SegmentEngine` 状态机和 `ADTS` 头生成
5. **把 `server.py` 拆成三层**：sync / summarize / web
6. **加端到端加密**：音频在上传前 AES 加密，密钥只在本地
7. **加跨天检索**：时间线 embedding + 向量检索

## 八、结论

**能自己用，不能给别人用。**

核心价值不在于代码本身，而在于它验证了几个判断：
- 手机端常驻录音在 Android 16 上可行，但必须接受「通知可见 + 不能自启」
- 远场录音的转写质量，取决于拾音信噪比而非模型大小
- 云端 ASR 的成本已经低到可以忽略，本地模型在这个场景没有优势
- 「能转写」和「有用」之间，隔着一个「价值筛选」

最后一个判断是这个项目最值得继续投入的方向：
一天 63 段录音里只有 32 条有效内容，如果日报不解决「什么值得看」，
用户第三天就会放弃。
