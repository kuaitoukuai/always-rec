# 设计决策与权衡

记录每个「看起来可以不一样」的选择，以及为什么没选另一条路。
这份文档的用途是让审查者知道哪些是权衡、哪些是疏忽。

---

## 1. 音频容器：ADTS 而不是 MP4

**选项**：MP4/M4A 容器 / ADTS 裸流

**选择**：ADTS

**理由**：
- 每帧自带头，文件被截断到任意位置都仍可解码播放
- ffmpeg / Whisper / 各家云 ASR 都直接吃，后端零适配
- 不需要 `MediaMuxer`，少一层封装和状态管理

**代价**：
- 体积比 MP4 大约 1%（每帧 7 字节头）
- 没有全局元数据（时长要自己算或读 meta）

**什么情况下该改**：如果需要存 24bit/48kHz 音乐级音频，ADTS 的固定头开销就不划算了。

---

## 2. VAD：自研能量法，不是 Silero

**选项**：Silero VAD（DNN）/ WebRTC VAD（GMM）/ 自研能量法

**选择**：自研能量法（相对阈值 + 双速噪声底），预留 WebRTC 替换点

**理由**：
- 24 小时常驻意味着每秒 50 次判定，一天 432 万次。DNN 推理的 CPU 唤醒
  耗电会盖过它省下的那点存储收益
- 能量法对「突然出现的人声」足够敏感，对「持续的背景音乐」会误判，
  但误判的代价只是多录一段空音频
- 零依赖，避免引入 native 库带来的 ABI / 体积问题

**代价**：
- 电视、短视频会被当成语音触发（实测 63 段里约一半是这类）
- 无法区分「人声」和「有节奏的噪声」

**缓解**：`onsetMs`（连续 60ms）和 `minSegmentMs`（1 秒）过滤瞬时噪声。
如果误触发率仍高，把 `onsetMs` 提到 150–200ms。

**什么情况下该改**：如果要做「只录我说的话」这种需求，必须上 DNN + 声纹。

---

## 3. 预缓冲：8 秒，且必须在 open 之前

**背景**：纯触发起录的方案，最常翻车的地方是切掉话头。

**选择**：idle 态持续写环形缓冲，触发时整段吐出

**关键实现细节**：`open()` 内部要 `ring.drainTo { enc.write(it) }`，
**顺序必须是先 open 后 drain**。如果写成「先 push 再 open」，
第一帧会被写两次或丢失。

**为什么是 8 秒**：话头通常在两三秒内说完，8 秒留足余量。
内存代价 8s × 16000 × 2B = 256KB，可忽略。

**代价**：每个片段开头会包含最多 8 秒的触发前音频，包含环境噪声。

---

## 4. 不申请 PARTIAL_WAKE_LOCK

**背景**：后台长时间录音，直觉上需要 wakelock 防止系统休眠。

**事实**：录音期间 `audioserver` 会自动持有 wakelock。应用层再申请一层，
只会让 CPU 无法进入低功耗状态，纯增耗电。

**这是很多人会踩的坑**：网上大量教程让你 `newWakeLock(PARTIAL_WAKE_LOCK)`，
那是 2015 年的写法。

**代价**：如果厂商 ROM 修改了 audioserver 行为（少见），可能真的会断。

## 5. 网盘当消息队列，而不是自建对象存储

**选项**：腾讯云 COS / 阿里云 OSS / 自建 MinIO / 百度网盘

**选择**：百度网盘（网页版接口）

**理由**：
- 零成本、零运维、天然跨设备
- 手机在外面（4G）也能传，不需要内网穿透
- 用户本来就有 2TB 空间，音频归档顺手完成

**代价（必须承认）**：
- **非官方接口**，百度随时可能改，没有 SLA
- **BDUSS 是完整账号凭证**，泄露等于交出网盘
- 上传速度受限于免费账号（实测约 1.5MB/s）
- 没有原子性：上传中断会留下半截文件
- `filemanager` 接口对 `/apps` 目录无效（errno=2），迁移只能重新上传

**什么情况下该改**：如果是团队使用，应该换成 S3 兼容存储 + 预签名 URL。

---

## 6. 百度网盘：网页版接口而非开放平台 OAuth

**选项**：开放平台（appKey + appSecret + 授权码）/ 网页版（app_id=250528 + BDUSS）

**选择**：网页版

**理由**：
- 开放平台需要应用审核，个人开发者门槛高
- 网页版接口和成熟的 `baidu_upload.py` 生态一致，后端和 App 能共用同一份 cookie
- 少了 token 刷新这一整条错误处理链

**代价**：见上一条的凭据风险。

## 7. 转写放在手机端（混合方案）

**背景**：最初设计是「手机只录，后端全包」。实际跑下来发现手机上要等 5–15 分钟
才能看到文字，体验不可接受。

**选择**：手机端做转写，后端做概要

**理由**：
- 用户要「立刻看到文字」，只能端上做
- 阿里云 ASR 直接吃 AAC，端上集成成本极低（一个 HTTP 请求）
- 转写文本随音频一起上传，后端复用，不重复计费

**代价**：
- API Key 存在手机里（`LocalConfig.kt`），反编译可提取
- 手机端不便于做复杂的后处理（繁简转换、重复折叠目前只在后端做）

**这是本项目最明显的架构妥协**，审查时值得重点质疑。

---

## 8. 转写结果本地缓存

**背景**：v0.1.0 早期版本只记录「哪些片段处理过」，不存文本。
结果每次调参重跑都要重新调 API，50 片要 1 分 39 秒。

**选择**：`data/transcripts/<id>.json` 按片段 id 缓存

**效果**：重跑从 99 秒降到 2 秒，且不重复计费。

**代价**：数据目录会随天数增长（约 1KB/片段，一天 100 片 = 100KB，可忽略）。

## 9. `START_NOT_STICKY`

**背景**：服务被杀后，`START_STICKY` 会自动重启，看起来更健壮。

**事实**：Android 14+ 下自动重启会崩溃，因为此时 App 在后台，
无权启动 microphone 类型前台服务。

**选择**：`START_NOT_STICKY` + 心跳监控 + 用户手动重开

**代价**：做不到真正的无人值守。这是平台限制，不是实现缺陷。

---

## 10. 后端不引数据库

**选择**：本地文件（JSON / Markdown）+ 目录结构表达状态

**理由**：
- 单机自用，数据量小（一天 100 个片段）
- 用 `ls` 和 `cat` 就能调试，不需要连 SQLite
- 便于用户直接读、直接改、直接备份

**代价**：
- 不支持并发写（目前单线程同步，没问题）
- 无法做复杂的跨天查询
- 文件数量增长后 `glob` 会变慢（估算 1 年后约 3.6 万个文件，仍在可接受范围）

**什么情况下该改**：需要「问上个月那个想法是什么」这类跨时间检索时，
必须上向量库，届时这层要重构。

## 11. 已知的不优雅之处

诚实列出，供审查参考：

1. **`LocalConfig.kt` 里存凭据** —— 应该改成从 `local.properties` 注入到 BuildConfig，
   目前是为了「改一个文件就能跑」的便利性牺牲了安全性
2. **`SummaryActivity` 用程序化 UI** —— 没有用 XML 布局，改动成本高
3. **`server.py` 单文件 500 行** —— 同步、摘要、页面混在一起，应该拆分
4. **没有单元测试** —— 全靠真机验证，回归成本高
5. **错误处理大量用 `runCatching{}.getOrDefault(false)`** —— 吞掉异常，
   线上问题难定位
6. **`Spool` 的状态用目录位置表达** —— 没有显式的失败状态，上传永久失败的文件会
   一直留在 pending 里直到 20 次重试后跳过
7. **中文硬编码在代码里** —— 没有做国际化，虽然短期不需要
